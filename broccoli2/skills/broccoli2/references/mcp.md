# Тулы BroccoliMcp

Сервер живёт внутри настольного приложения: оно держит открытые схемы и показывает человеку, что
происходит. Если тулы не отвечают — приложение не запущено, попроси человека его поднять.

## Ответ мутирующего тула

Три части, всегда:

1. **подтверждение** — сделано или отказ с причиной;
2. **последствия** — что изменилось, в именах нод и портов;
3. **здоровье схемы** — нод, связей, некорректных связей, ошибок, предупреждений, компилируется ли.

Здоровье важнее подтверждения: правка в одном месте может сломать другой конец схемы, и видно это
только по нему.

## Состав

| Тул | Что делает |
|---|---|
| `nodes_find` | Ищет ноды по подстроке в типе, названии, описании. Без запроса — весь состав |
| `nodes_describe` | Описание ноды и состав портов, с которым она заводится |
| `scheme_list` | Открытые схемы и файлы в рабочей папке |
| `scheme_new` | Новая пустая схема. На диск попадёт только при `scheme_save` |
| `scheme_open` | Открыть из файла. `readOnly` — на просмотр, править нельзя |
| `scheme_close` | Закрыть. Несохранённое теряется |
| `scheme_save` | Записать в файл |
| `scheme_describe` | Схема целиком: строка на ноду плюс здоровье. Он же ресинк |
| `scheme_inspect` | Ноды подробно: у портов итоговый, желаемый и допустимые типы, связи с типами концов |
| `scheme_check` | Некорректные связи, диагностики, годность к отправке |
| `scheme_apply` | Применить описание схемы целиком. Основной путь сборки |
| `scheme_add_node` | Добавить ноду |
| `scheme_remove_node` | Удалить ноду со связями |
| `scheme_link` | Связать выход со входом |
| `scheme_unlink` | Разорвать связь |
| `scheme_set_value` | Задать значение входа |
| `scheme_select_definition` | Переключить вход на другое определение |

## Ярлыки нод

Нода адресуется ярлыком вида `n8f3a12` — это короткий вид её идентификатора. Он не меняется при
сохранении и открытии заново: адрес, записанный вчера, показывает на ту же ноду сегодня.

В описании (`scheme_apply`) ноды называют своими ярлыками — `model`, `walls`. Это ярлыки описания,
а не схемы: они живут, пока схема открыта, и нужны, чтобы повторное применение того же описания
узнало уже созданные ноды. Отчёт о применении показывает пару — какой ярлык описания какой ноде
достался.

## Описание схемы

`scheme_apply` принимает не схему, а инструкцию:

```json
{"nodes": [
  {"name": "model", "type": "Model"},
  {"name": "props", "type": "Properties", "links": {"Object": ["model.Result"]}},
  {"name": "walls", "type": "CategoryFilter", "values": {"Category": "OST_Walls"}},
  {"name": "filter", "type": "Where",
   "links": {"Input": ["props.Elements"], "Selector": ["walls.Result"]}},
  {"name": "error", "type": "SaveError",
   "values": {"Text": "Стена без типа"}, "links": {"Input": ["filter.Result"]}}
]}
```

Свойства ноды: `name` — ярлык описания, `type` — тип ноды, `values` — значения входов,
`definitions` — ключи определений, `links` — источники связей вида `ярлык.Порт`.

Описание **идемпотентно**: повторное применение того же описания ничего не меняет. Нода узнаётся
по ярлыку, связь — по паре концов, равное значение конструктор изменением не считает. Поэтому
описание можно применять по частям и дополнять.

Ссылаться можно и на ноды, уже лежащие в схеме, — по их собственным ярлыкам.

Порядок внутри описания значения не имеет: связи создаются в порядке потока данных, а селекторы —
после потоков, потому что иначе согласование типов уйдёт впустую.

Флаг `replace` удаляет из схемы всё, чего описание не называет. Без него лишнее остаётся и
попадает в расхождения отчёта.

## Когда что

- Собираешь схему с нуля или переделываешь крупно — `scheme_apply`.
- Точечная правка, особенно в чужой схеме — императивные тулы.
- Потерял представление о схеме — `scheme_describe`.
- Связь покраснела — `scheme_inspect` на её концах.
