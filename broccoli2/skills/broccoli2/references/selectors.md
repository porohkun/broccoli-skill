# Селекторы

Селектор — значение, которое нода-потребитель применяет к каждому объекту своего потока по
отдельности. Тип: `ISelector<Объект, Результат>`. У фильтров результат `Boolean` — «да/нет»; у
`GroupBy` — ключ группы, у `Sum` — число, у `SelectMany` — поток.

Селектор не фильтрует сам. Он только отвечает; отсеивает, группирует или складывает — та нода,
которой он отдан.

## Откуда берутся

| Нода | Что отдаёт |
|---|---|
| `CategoryFilter` | «элемент нужной категории»; сворачивается в быстрый фильтр Revit |
| `ElementKindFilter` | «элемент нужного вида»; быстрый фильтр, а `Where` с ним уточняет тип потока |
| `ParameterFilter` | «параметр сравнился со значением»; быстрый там, где Revit умеет спросить параметр |
| `CombineFilter` | несколько селекторов, склеенных через И или ИЛИ |
| `CustomSelector` | функцию, собранную нодами: от `CustomSelectorBase` к входу Output |
| `ExpressionSelector` | вычисление выражением на C# |

## Кто их потребляет

| Нода | Что ждёт от селектора |
|---|---|
| `Where` | одно «да/нет» на объект |
| `GroupBy` | одно значение-ключ на объект |
| `Sum` | одно число на объект |
| `SelectMany` | поток на объект; без селектора — разворачивает группы |
| `SplitBy` | селектор с заранее известными вариантами ответа: категории, вид, параметр |

## Селектор из нод — функция

`CustomSelector` вместе со своей `CustomSelectorBase` задаёт функцию «объект → значение». Тело
функции — ноды, которые зависят по связям от выхода Element базы, не проходя через сам
`CustomSelector`. Потребитель вызывает функцию на каждом объекте: сначала собирает свой вход
целиком, потом считает тело для каждого объекта заново.

- **Внутри или снаружи.** Нода, которая от объекта не зависит, — `Model`, `Properties` над
  документом, `Vector` с числами, — считается один раз снаружи, и тело получает её значения готовыми.
  Отсюда: всё, что не про объект, держи вне тела — оно не пересчитывается на каждом объекте.
- **Внутри работают все потоковые ноды**: `Properties`, `Where`, `GroupBy`, `Length`, `Sum`,
  `Comparison`, геометрия, быстрые фильтры, якоря. Селектор внутри селектора — функция внутри
  функции; нода, зависящая от объектов нескольких вложенных селекторов, считается в самом
  вложенном.
- **Внутри не сохраняют**: `SaveError`, `SaveMessage`, `ResultPercentBase`, зависящие от объекта, —
  ошибка сборки. Наружу значение выходит только через `CustomSelector`.
- **Одно значение или поток.** Для `Where`, `Sum`, `GroupBy` функция обязана дать на объект ровно
  одно значение: поток вместо значения останавливает проверку при исполнении с текстом, сколько
  значений получено и в какой ноде, а `GroupBy` такой селектор не примет уже при сборке. Для
  `SelectMany` — наоборот, тело отдаёт поток, и берутся все его значения.
- **Тип объекта приходит справа.** Потребитель пишет тип объекта в `CustomSelector`, тот — в свою
  базу. Пока селектор не связан с потребителем, Element — `Object`, и у `Properties` над ним выходов
  нет. `scheme_apply` откладывает такие связи сам: тело можно описать в любом порядке.
- **Состав проверяется при сборке**: селектор без базы или без связи в Output, база, чей Element
  читают, а Base не подключён, нода, зависящая от объектов двух селекторов, ни один из которых не
  вложен в другой, — ошибки сборки, которые `scheme_check` показывает строкой «не компилируется».
- **Цена.** Функция считается на каждом объекте заново. «Каждый с каждым» по всей модели — N × M
  вызовов: сначала разбей объекты на группы (`GroupBy` по листу или уровню) и сравнивай внутри
  групп. Пример — geometry.md.

## Селектор с кодом

`ExpressionSelector` — условие или вычисление телом лямбды на C#.

- Входной и желаемый типы проставляет потребитель — их не задают руками.
- Текст проверяется Roslyn'ом до исполнения: `scheme_check` покажет ошибки компиляции выражения
  там же, где остальные диагностики. Язык — C# 10.
- Тип ответа — тип выражения. Если оно неявно приводится к желаемому — целое к `double`, —
  приводится; иначе потребитель остановит схему при сборке.
- Песочницы нет: код исполняется в том же процессе. Не пиши в выражении ничего, кроме вычисления
  над объектом.
- Быстрым фильтром не сворачивается и для `SelectMany` не годится.

Когда что выбирать: фильтры — для простого отбора и ради быстрых фильтров; `CustomSelector` — когда
условие собирается из нод и его видно на канве; `ExpressionSelector` — когда условие проще написать,
чем собрать, или нужно сравнить то, что нодами не сравнить, например ID элементов.

## Согласование типов

Потребитель сам объявляет, какой селектор ему нужен, и пишет это в селекторную ноду:

- тип объекта — из типа своего потока;
- тип результата — из своей задачи (`Where` — `Boolean`, `Sum` — число, `SelectMany` — поток).

Отсюда правило порядка: **сначала поток, потом селектор**. `scheme_apply` соблюдает его сам; в
точечной правке связывай Input раньше Selector.

Селектор по более общему объекту подходит потоку более частных: `ISelector<IElement, Boolean>`
ляжет на поток `IFlow<IWall>`. Обратное неверно.

`CombineFilter` тип объекта своим условиям не передаёт: у `CustomSelector` и `ExpressionSelector`
внутри него InputType задают руками, например `IElement`.

## Ограничения

- Селектор приходит **ровно одной связью**. Поток селекторов не поддержан: если `CategoryFilter`
  получил категории связью-потоком, он отдаст поток селекторов, и `Where` такую схему не выполнит.
- Несколько условий складывает `CombineFilter`, а не несколько связей в один порт. Если среди
  условий есть селектор-функция, склейка сама становится функцией: условия считаются слева
  направо, и быстрого фильтра у неё нет.
- Категория у `CategoryFilter` и имя параметра у `ParameterFilter` внутри селектора вписываются
  значением, а не приходят связью.
